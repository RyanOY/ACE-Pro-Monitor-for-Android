## 1. 功能边界

v0.2 通过手机 USB OTG + USB-RS485 控制 Anycubic ACE2 Pro。烘干相关能力如下：

**烘干是怎么发生的**：ACE2 Pro 料盒里有 PTC 加热片和循环风扇，设备固件用 NTC 测温、自己闭环控制加热功率；App 只负责通过 RS-485 下发「目标温度 + 时长」（或全零停止），然后轮询状态。也就是说温度能否稳住取决于设备固件，App 不参与调温，也没有独立的过温保护——断线时更无法兜底。

| 能做 | 说明 |
|---|---|
| 连接设备 | 230400 baud / 8N1 / 无流控；自动发现设备、分配总线地址 1、读取固件版本 |
| 启动烘干 | 目标温度 30–65 ℃、时长 10–1440 分钟；启动前二次确认；`auto_roll` 固定关闭 |
| 停止烘干 | 发送全零 `DRYING` 请求；「停止烘干」按钮在就绪后常驻可用 |
| 状态轮询 | 每 2 s 一次 `GET_STATUS`：工作状态、箱内温度/湿度、烘干状态、目标温度、剩余时间 |
| 排障 | 保留 v0.1 的原始帧 hex 收发日志与手动 hex 发送 |

| 不能做 | 说明 |
|---|---|
| RFID | 不读标签、不写标签，不识别耗材类型 |
| 固件升级（IAP） | 未实现；命令 5 路径未验证，刷机有变砖风险 |
| 多设备 | 固定 `device_id=1`，只支持单台；多机总线寻址未做 |
| 其他执行器 | 进料/回抽、风扇、阀门、闪灯等命令未接入界面 |
| 温度闭环 | App 只下发目标温度，PTC 由设备固件自己控制；App 不参与调温、不做过温保护 |
| 断电保护 | USB 断开、App 退出、手机没电时 **不会**自动停止加热（见 2.3） |

## 2. 安全须知（先读再操作）

1. **这是真实加热。** PTC 在料盒里升温，旁边就是纸盒、塑料件和线材。烘干全程必须有人值守；离开前先点「停止烘干」并确认状态回到「已停止」。**无人值守的加热是本项目最危险的操作。**
2. **温度上限 65 ℃。** App 硬限制 30–65 ℃（与参考实现 Klipper 配置 `max_dryer_temperature = 65` 对齐），超范围直接拒绝；时长限制 10–1440 分钟。不要为了「快一点」拉高温度：超过线材耐温会软化、变形、释放气味。
3. **断线 ≠ 停止。** RS-485 半双工总线只有一条，USB 松脱 / App 被杀 / 手机没电时，App 无法再发送停止命令，设备会按固件逻辑继续加热到设定时长。遇到无法停止的情况，**直接断设备电源**（按设备说明书操作），不要只拔 USB 线。
4. **通风与防火。** 设备周围保持通风、远离易燃物；不要在密闭柜、纸箱里烘干；旁边要有可用的断电手段。闻到焦味或塑料味立即停止并断电。
5. **首次试机。** 先 40–45 ℃ / 10–30 分钟短时试跑，人守在旁边，观察：面板是否显示升温、温度是否在合理范围内缓慢上升、有无异响异味。出现「不升温 / 温度飙升 / 目标与实际差太远」立即停止。
6. **电气安全。** 断电后再接线；只接 A/B/GND，**不接设备的 5V**；做好共地；不要热插拔设备侧的连接器。
7. **单主站。** 不要把手机和打印机主机同时接在同一条 RS-485 总线上；切换主机前先断开上一台。半双工没有仲裁，两个主站会互相打断、状态分裂。
8. **材料与料盘。** 只烘你了解耐温的线材；纸料盘 / 薄塑料料盘在 60 ℃ 以上可能变形；不要烘带金属件、电池或不明物体的东西。
9. **故障即停。** 状态卡显示「故障」或应答码非 0 时，立即停止、断电排查（第 8 节），不要反复重试。

## 4. 硬件与接线

- **转换器**：USB 转 RS-485。官方/兼容 ACE2 线缆是 **CH343（`1a86:55d3`）**，实测在 `usb-serial-for-android 3.8.1` 下以 CDC-ACM 枚举、被 `CdcAcmSerialDriver` 接住，**可直接使用**（见 [`HARDWARE-VERIFICATION.md`](./HARDWARE-VERIFICATION.md)）；CH340 / CH341A / CP210x / FTDI / PL2303 同样是常见选择。
- **接线**：转换器 A/B → 设备 RS-485 A/B，GND 共地；只用 3 根线（A / B / GND），**不接设备 5V**。A/B 接反的典型症状是「完全没回包」，可断电后对调试一次。
- **串口参数**：230400 baud、8 数据位、无校验、1 停止位、无硬件流控（App 固定 8N1，波特率下拉框默认 230400）。
- **手机**：需支持 USB Host / OTG；插线后系统会弹 USB 权限，选「允许」。
- **单主站**：同一时刻只能有一个主站控制设备（见第 2 节第 7 条）。

## 5. 操作步骤

前置：设备已上电、料盒内装好需要烘干的线材、盒盖关闭、周围通风。

1. 接好线，打开 App。
2. 点「连接 USB 串口」→ 系统弹 USB 授权 → 允许。
3. 日志出现 `串口已打开 @ 230400 8N1 [...]`，状态栏显示「已连接 · ACE2 DISCOVERING」。
4. 等待自动握手（约 1–3 s），日志依次出现：

   ```text
   → DISCOVER_DEVICE #1 (...)
   ← DISCOVER_DEVICE #1 flags=0x00 (...)
   状态：ASSIGNING · 发现设备 UID=...，分配总线地址 1
   → ASSIGN_DEVICE_ID #2 (...)
   设备地址分配成功：device_id=1
   → GET_INFO #3 (...)
   固件版本：V1.x.y（boot V1.x.y）
   状态：READY · ACE2 已就绪，开始周期查询状态
   ← GET_STATUS #4 flags=0x81 (...)
   ```

5. 点「查询状态」可强制刷新一次（日志 `手动查询状态 …`）。
6. 输入目标温度（30–65）与时长（10–1440），点「启动烘干」。
7. 在确认对话框里核对参数与安全提示，点「确认」。日志应出现：

   ```text
   用户确认：启动烘干 55℃ / 240 分钟
   → 启动烘干：55℃ / 240 分钟
   → DRYING(start 55C 240min) #N (1/3) FF AA ...（实际帧见 6.4）
   ← DRYING #N flags=0x81 08 00
   ✔ 已启动烘干
   ```

8. 观察状态卡：`烘干：烘干中 · 目标 55 ℃ · 当前 xx ℃ · 剩余 239分58秒`。当前温度接近目标需要时间（PTC 加热 + 箱体传热），中途波动正常；剩余时间每 2 s 刷新。
9. 点「停止烘干」→ 确认 → 日志 `→ DRYING(stop) ...` 与 `✔ 已停止烘干`；状态回到「已停止」，温度逐步回落（PTC 有余温，不是立刻变凉）。
10. 点「断开串口」只关闭 App 的串口会话（停止轮询、停止日志），**不会停止设备正在进行的烘干**；要停就先点「停止烘干」。

上面各步对应的请求帧（应答字段见 6.6 / 6.8）：

| 操作 | cmd | 请求 flags | payload | 说明 |
|---|---|---|---|---|
| 发现设备 | 0 `DISCOVER_DEVICE` | `0x00`（广播） | 空 | 应答带回 uid1/uid2/uid3 |
| 分配地址 | 1 `ASSIGN_DEVICE_ID` | `0x00`（广播） | 字段 1–3 = uid1–3，字段 4 = `device_id=1` | 期望 `code=0` |
| 读固件版本 | 7 `GET_INFO` | `0x01` | 空 | 字段 1 version / 2 boot_version；失败不阻塞就绪 |
| 轮询/手动查询 | 6 `GET_STATUS` | `0x01` | 空 | 应答见 6.8 |
| 启动烘干 | 11 `DRYING` | `0x01` | 温度 ℃ + 时长（分钟）+ `auto_roll=false` | 见 6.3 / 6.4 |
| 停止烘干 | 11 `DRYING` | `0x01` | 全零 | payload 6 字节 |

## 6. 协议详解

### 6.1 帧格式

请求与应答同格式，应答的 flags 最高位置 1：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `0xFF` | 帧头 1 |
| 1 | 1 | `0xAA` | 帧头 2 |
| 2 | 1 | flags | 请求：低 7 位是总线地址（本 App 用 1）；`DISCOVER_DEVICE` / `ASSIGN_DEVICE_ID` 用 0 广播。应答：`0x80 \| 地址`，即 `0x81` |
| 3–4 | 2 | id | 请求序号，16 位小端；应答原样回填 |
| 5 | 1 | cmd | 命令号（本文只用到 0 / 1 / 6 / 7 / 11） |
| 6 | 1 | len | payload 长度，0–100 |
| 7 … 7+len−1 | len | payload | protobuf 编码的参数 |
| 7+len … 8+len | 2 | crc16 | CRC16/MCRF4XX，**小端** |
| 9+len | 1 | `0xFE` | 帧尾 |

- **CRC 范围**：`frame[2 .. 7+len)`，即 `flags + id + cmd + len + payload`，**不含**帧头、CRC 自身和帧尾。
- **CRC 参数**：CRC-16/MCRF4XX，反射多项式 `0x8408`，初值 `0xFFFF`，无最终异或；黄金校验值 `CRC16("123456789") = 0x6F91`。
- **最小帧长**：10 字节（空 payload）。

### 6.2 v0.2 实际使用的命令

| cmd | 名称 | v0.2 用途 |
|---|---|---|
| 0 | `DISCOVER_DEVICE` | 连接后广播发现设备，取应答里的 uid1/uid2/uid3 |
| 1 | `ASSIGN_DEVICE_ID` | 用 uid1..3 + `device_id=1` 分配总线地址 |
| 6 | `GET_STATUS` | 每 2 s 轮询状态；点「查询状态」时立即发一次 |
| 7 | `GET_INFO` | 握手时读固件版本（可选，失败也会继续进入就绪） |
| 11 | `DRYING` | 启动 / 停止烘干 |

其余命令（进料、RFID、闪灯、升级等）未接入界面，资料见 [`ace2-protocol-notes.md`](./ace2-protocol-notes.md)。

### 6.3 `DRYING` 请求 payload

payload 是 protobuf 的 `DryingRequest`，字段号来自参考实现：

| 字段号 | 类型 | 值 | 说明 |
|---|---|---|---|
| 1 | uint32 | 目标温度（℃） | 30–65；**0 表示停止** |
| 2 | uint32 | 时长（**分钟**） | 10–1440；**0 表示停止** |
| 3 | bool | `auto_roll` | v0.2 固定 `false`（不转卷盘） |

停止烘干 = 三个字段都写 0：`08 00 10 00 18 00`（payload 6 字节）。

> protobuf 规范允许省略值为 0 的字段（停止也可以发空 payload）；本 App 选择显式写 0，语义等价，解析端按缺省值 0 处理。

### 6.4 真实请求帧：启动烘干 55 ℃ / 240 分钟

```
FF AA 01 05 00 0B 07 08 37 10 F0 01 18 00 78 E3 FE
```

逐字节解释：

| 偏移 | 字节 | 含义 |
|---|---|---|
| 0–1 | `FF AA` | 帧头 |
| 2 | `01` | flags = 1：设备地址 1（请求方向，bit7 = 0） |
| 3 | `05` | id 低字节 |
| 4 | `00` | id 高字节 → 请求 id = 5 |
| 5 | `0B` | cmd = 11（`DRYING`） |
| 6 | `07` | payload 长度 = 7 字节 |
| 7 | `08` | 字段 1 的 key：`(1<<3) \| 0` = 0x08（varint） |
| 8 | `37` | 字段 1 的值 = 55 → **目标温度 55 ℃** |
| 9 | `10` | 字段 2 的 key：`(2<<3) \| 0` = 0x10（varint） |
| 10–11 | `F0 01` | 字段 2 的值：varint 解码 `0x70 + (0x01<<7) = 240` → **时长 240 分钟** |
| 12 | `18` | 字段 3 的 key：`(3<<3) \| 0` = 0x18（varint bool） |
| 13 | `00` | 字段 3 的值 = false → `auto_roll` 关闭 |
| 14–15 | `78 E3` | CRC16/MCRF4XX = `0xE378`（小端存储） |
| 16 | `FE` | 帧尾 |

帧长 17 字节。

> ⚠️ id、温度、时长任一改动都会改变 CRC（id 也参与计算）。示例取 id = 5 是为了和 `tools/ace2_vectors.json` 的 `start_drying` 黄金向量逐字节对齐；App 运行时 id 从 1 递增，握手和每 2 s 的状态轮询都会占用 id，所以**真实日志里的 id（以及 CRC）通常不等于 5**。改动后必须整帧重算，不能只改一个字节。
>
> 该帧与 `tools/ace2_vectors.json` 中由参考实现生成的黄金向量 `start_drying` 逐字节一致；`python3 tools/verify_ace2.py` 会做同样的比对（当前 120 项通过）。
>
> ✅ **真机实测帧**（固件 V1.1.22，目标 50 ℃ / 240 min，id=9）：
> `FF AA 01 09 00 0B 07 08 32 10 F0 01 18 00 00 15 FE` → 设备回 `FF AA 81 09 00 0B 00 52 AC FE`（空 payload = code 0 成功），随后状态里 `field2 = {1:2 烘干中, 2:50, 3:14400s, 4:14398s}` 倒计时正常。完整记录见 [`HARDWARE-VERIFICATION.md`](./HARDWARE-VERIFICATION.md)。

停止帧（id = 6，payload 全零）：

```
FF AA 01 06 00 0B 06 08 00 10 00 18 00 61 0B FE
```

查询状态帧（id = 7，空 payload）：

```
FF AA 01 07 00 06 00 3D 38 FE
```

### 6.5 CRC 自校验脚本

把下面脚本保存为 `verify_crc.py`，运行 `python3 verify_crc.py`。它独立实现 CRC16/MCRF4XX 与组帧，并用它自己算出的 CRC 重新校验上面三条帧：

```python
def crc16(data, crc=0xFFFF):
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0x8408 if crc & 1 else crc >> 1
    return crc & 0xFFFF

def le16(v):
    return bytes([v & 0xFF, v >> 8])

def varint(v):
    out = bytearray()
    while v > 0x7F:
        out.append((v & 0x7F) | 0x80)
        v >>= 7
    out.append(v)
    return bytes(out)

def pb_uint(field, value):  # protobuf varint 字段
    return varint(field << 3) + varint(value)

def drying_payload(temp_c, minutes, auto_roll=False):
    # 与 Ace2Protocol.dryingPayload() 一致：1=温度，2=分钟，3=auto_roll
    return pb_uint(1, temp_c) + pb_uint(2, minutes) + pb_uint(3, int(auto_roll))

def build_frame(flags, request_id, cmd, payload):
    inner = bytes([flags]) + le16(request_id) + bytes([cmd, len(payload)]) + payload
    return b"\xff\xaa" + inner + le16(crc16(inner)) + b"\xfe"

def verify(hex_text):
    raw = bytes.fromhex(hex_text)
    length = raw[6]
    inner = raw[2:7 + length]
    crc = raw[7 + length] | (raw[8 + length] << 8)
    assert raw[:2] == b"\xff\xaa" and raw[-1] == 0xFE
    assert crc16(inner) == crc, "CRC 不匹配"
    return raw, crc

print("黄金值 CRC16/MCRF4XX('123456789') = 0x%04X" % crc16(b"123456789"))
for label, args in [
    ("启动烘干 55℃/240min (id=5)", (0x01, 5, 11, drying_payload(55, 240))),
    ("停止烘干 (id=6)",            (0x01, 6, 11, drying_payload(0, 0, False))),
    ("查询状态 GET_STATUS (id=7)", (0x01, 7, 6, b"")),
]:
    f = build_frame(*args)
    raw, crc = verify(f.hex())
    print("%-26s: %s" % (label, f.hex(" ").upper()))
    print("  长度=%dB  cmd=%d  CRC=0x%04X ✔" % (len(raw), raw[5], crc))
```

实际运行输出（python3，2026-11）：

```text
黄金值 CRC16/MCRF4XX('123456789') = 0x6F91
启动烘干 55℃/240min (id=5)    : FF AA 01 05 00 0B 07 08 37 10 F0 01 18 00 78 E3 FE
  长度=17B  cmd=11  CRC=0xE378 ✔
停止烘干 (id=6)               : FF AA 01 06 00 0B 06 08 00 10 00 18 00 61 0B FE
  长度=16B  cmd=11  CRC=0x0B61 ✔
查询状态 GET_STATUS (id=7)    : FF AA 01 07 00 06 00 3D 38 FE
  长度=10B  cmd=6  CRC=0x383D ✔
```

### 6.6 应答

- 应答 flags = `0x80 | 设备地址` → `0x81`，id 与请求相同；payload 为 protobuf。
- `DRYING` 的应答是 `GenericResponse{code=1}`：成功时 payload 为 `08 00`（字段 1 = 0）。
- App 对 code 非 0 的显示为 `指令失败：code=N NAME`。

| code | 名称 | 含义（参考实现） |
|---|---|---|
| 0 | SUCCESS | 成功 |
| 1 | PARAM_ERROR | 参数错误（超范围） |
| 2 | FORBIDDEN | 设备忙 / 不允许 |
| 3 | FAILED | 执行失败 |
| 6 | READFAILED | RFID 读取失败（烘干不用） |
| 400 | UNSUPPORTED | App 兜底文案（协议未定义，仅用于显示） |

- 单帧超时 1200 ms（`DRYING` 2000 ms），最多重试 3 次；同一时刻只允许一个在途请求，成功后才发下一条。
- 注意：**发送成功 ≠ 动作一定执行**（例如设备已在停止过程中）。以随后的 `GET_STATUS` 状态为准。

### 6.7 单位差异（最容易踩的坑）

| 位置 | 字段 | 单位 |
|---|---|---|
| `DRYING` 请求 | `duration`（字段 2） | **分钟** |
| `GET_STATUS` → DryStatus 字段 3 | `duration` 总时长 | **秒** |
| `GET_STATUS` → DryStatus 字段 4 | `remain_time` 剩余 | **秒** |

两者相差 60 倍。App 显示时把剩余秒换算成 `x分y秒`。

### 6.8 `GET_STATUS` 应答字段

`StatusResponse`（App 实际解析的字段）：

| 字段 | 类型 | 含义 | App 用法 |
|---|---|---|---|
| 1 | uint32 | 工作状态：0 初始化 / 1 就绪 / 2 忙碌 / 3 升级中 | 状态卡「ACE2」段 |
| 2 | DryStatus | 烘干子消息（见下表） | 状态卡「烘干」段 |
| 3 | uint32 | 箱内当前温度 ℃ | 状态卡温度 |
| 4 | uint32 | 湿度 % | 状态卡湿度 |
| 7 | uint32 | feed assist 计数 | v0.2 不显示 |
| 9 | repeated | 槽位列表（字段 1 状态码、字段 2 有料标志） | v0.2 不显示 |

DryStatus（字段 2 的子消息）：

| 字段 | 类型 | 含义 |
|---|---|---|
| 1 | uint32 | 状态码：0 停止 / 1 烘干中 / 2 烘干中 / 3 停止 / 4 PTC 故障 / 5 NTC 故障 |
| 2 | uint32 | 目标温度 ℃（为 0 时 App 用最近一次下发的温度兜底显示） |
| 3 | uint32 | 设定总时长（**秒**） |
| 4 | uint32 | 剩余时间（**秒**） |

> 参考实现还约定字段 1 的低 4 位是状态码、bit6/bit7 是 `auto_roll_allowed` / `rotisserie_active`。App 目前按裸值查表：如果设备把高位也置上，状态会显示「未知」——已知限制，需要真机确认后再改。

## 7. 常见问题

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 日志「未发现 USB 串口设备」 | 手机 OTG 未开 / 转接线松 / 线只充电 / 芯片无驱动 / 插着别的 USB 设备 | 换支持 OTG 的转接头；只留 RS-485 适配器；CH343 / CH340 / CP210x 均已验证或可用 |
| 「未识别该设备的串口驱动」 | 芯片不在支持列表 | 换 CH343（CDC-ACM，已实测）/ CH340 / CH341A / CP210x / FTDI / PL2303 |
| 「openDevice 返回 null」 | 没授权 / 被其他 App 占用 | 重新插拔并允许授权；关掉串口助手类 App |
| 连接后「发现失败：设备无应答」 | A/B 接反、没共地、波特率不是 230400、设备休眠、打印机主机占着总线 | 断电对调 A/B；共地；确认 230400；按设备按键唤醒；断开打印机主机 |
| 「分配设备地址被拒绝：code=…」 | 另一主站占用 / 设备忙 | 断开打印机主机后重新连接 |
| 启动烘干 `code=1 PARAM_ERROR` | 温度或时长超范围（设备端可能更严格） | 换成 40–60 ℃ / 30–120 分钟先试 |
| 启动烘干 `code=2 FORBIDDEN` | 设备忙（进料、升级、其他动作中） | 等状态回到「就绪」再试 |
| 返回成功但不升温 | 目标 ≤ 当前温度；设备处于停止/故障态；固件语义与逆向结论不同 | 看 `GET_STATUS` 的烘干状态码与当前温度；把目标设到明显高于当前温度（如 55）再试；仍不升温就停止排查 |
| 剩余时间不动 | 轮询超时断开 / 设备已停止 / USB 掉线 | 看日志是否还有 `← GET_STATUS`；重新连接 |
| 温度一直显示 0 | 固件字段语义与逆向结论不同（其他固件版本可能不同） | 本机实测 field3 = 箱内温度（空闲 22 ℃）、field4 = 湿度；若你的固件显示 0，停止烘干并保留原始 hex 日志排查（见第 9 节） |
| 停止后仍然很热 | PTC 余温，箱体降温需要时间 | 确认状态「已停止」且剩余时间不再减少即可 |
| App 崩溃 / 断线后还在加热 | 见 2.3 | 立即断设备电源 |

## 8. 故障码 4 / 5

- DryStatus 状态码 **4 = PTC 故障**、**5 = NTC 故障**（参考实现命名），状态卡会显示「故障」并变红。
- 处理顺序：点「停止烘干」→ 确认状态回到停止、剩余时间不再减少 → **断设备电源** → 检查 PTC 加热片和风扇是否被堵、NTC 探头线是否松动/短路、环境温度是否异常。
- 故障排除前不要再启动烘干；反复硬发命令不能解决硬件故障。
